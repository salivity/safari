The Role of LLInt in Safari's JavaScript Engine

This article explores the primary purpose of the Low Level Interpreter (LLInt), the foundational execution tier within JavaScriptCore, the engine that powers the Safari web browser. By examining how the LLInt processes bytecode, prioritizes rapid startup times, reduces memory overhead, and collects vital profiling data for Just-In-Time (JIT) compilers, this guide explains why this initial interpreter tier is essential for fast and efficient web browsing.

Immediate Execution and Fast Startup

The primary purpose of the LLInt is to execute JavaScript code as quickly as possible after a webpage loads. When Safari downloads a JavaScript file, the JavaScriptCore (JSC) engine parses the text into a compact intermediate representation called bytecode.

Instead of waiting for a compiler to translate this bytecode into complex machine code—a process that consumes significant time and CPU power—the LLInt begins executing the bytecode immediately. Because a large portion of JavaScript on the web is only executed once during page initialization, compiling it all into machine code would actually slow the browser down. The LLInt ensures near-zero startup latency.

Minimizing Memory Overhead

Compiling JavaScript into native machine code via a JIT compiler requires a substantial amount of memory. If Safari compiled every script on a complex webpage, the browser's memory footprint would skyrocket, leading to sluggish performance, especially on mobile devices like iPhones and iPads.

The LLInt solves this by executing the lightweight bytecode directly. By keeping rarely used code in the LLInt tier, Safari conserves system memory and saves battery life, reserving heavy compilation resources only for the code that truly needs it.

Profiling Code for Higher Tiers

JavaScriptCore is a multi-tiered engine. Besides the LLInt, it includes the Baseline JIT, the Data Flow Graph (DFG) JIT, and the Faster Than Light (FTL) JIT. The LLInt acts as a filter and a scout for these higher, faster tiers.

As the LLInt executes code, it performs two critical tasks:

  • Counting executions: It tracks how many times a function is called or how many times a loop iterates. When a piece of code crosses a specific threshold, it is flagged as "warm" or "hot" and is promoted to the next tier for compilation.
  • Type profiling: JavaScript is dynamically typed, meaning a variable can hold a number one moment and a string the next. The LLInt observes and records the data types flowing through variables and functions. When the code is promoted to the optimizing JIT compilers, they use the LLInt’s recorded data to make educated guesses and generate highly optimized machine code.

Seamless Tier Transitions

Unlike traditional interpreters written in C++, the LLInt is written in a portable assembly language called Offlineasm. It is specifically designed to use the exact same register and stack layout conventions as the JIT compilers that follow it.

Because the LLInt mimics the architecture of the JIT tiers, JavaScriptCore can easily pause execution in the middle of a slow-running loop in the LLInt and seamlessly switch to newly compiled JIT code. This process, known as On-Stack Replacement (OSR), is only possible because the LLInt is engineered to align perfectly with the rest of the pipeline.
